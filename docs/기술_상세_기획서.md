## 1.2 핵심 설계 원칙 및 불변 규칙

| 원칙 | 설계 내용 | 구현 위치 |
| --- | --- | --- |
| **① 신청이 먼저, 가입은 선택** | 회원가입 없이 접수하고, 접수할 때 정한 **4자리 PIN**과 접수번호(또는 연락처)로 진행 상황을 조회합니다. 회원 로그인은 이름·기본 수거지 자동 채움과 내역 모아 보기용입니다. | `C-02` · `C-04` · `POST /api/applications` |
| **② 1건 신청 : N개 품목 독립 관리** | 한 신청에 1~20개 품목을 담고, 상태·처리 구분·판매 마감일·반출 일정은 품목(`application_items`) 단위로 관리합니다. | `src/server/db.ts` · `A-04` · `PATCH /api/admin/items/:itemId` |
| **③ 이사일 역산 일정** | `희망 반출일 ≤ 이사일`(접수 시, 서버), `판매 마감일 ≤ 이사일`(관리자 저장 시, 서버)을 강제합니다. 클라이언트는 날짜 입력에 `min=오늘`만 걸고 선후 검사는 서버 `422`에 맡깁니다. | `services/applications.ts` `validatePayload` · `updateItemWorkflow` |
| **④ 공개 범위는 서버 직렬화가 결정** | 고객 응답은 필드를 하나씩 골라 담는 `toPublicApplicationDto`로 만들어 `admin_memo`·`admin_item_memo`·`lookup_pin_hash`가 구조적으로 들어갈 수 없습니다. | `src/server/services/applications.ts` |
| **⑤ 화면·쿠키 분리** | 고객 화면(`/`, `index.html`, 쿠키 `fr_customer`·`fr_lookup`)과 관리자 화면(`/admin`, `admin.html`, 쿠키 `fr_admin`)은 HTML·스크립트·쿠키가 따로입니다. 고객 로그아웃은 관리자 세션을 끊지 않습니다. | `public/index.html` · `public/admin.html` · `src/server/lib.ts` `COOKIES` |
| **⑥ 집 안 사진의 위치정보 제거** | 매직 바이트로 형식을 판정하고, JPEG의 `APP1`(EXIF/GPS/XMP)과 PNG의 `eXIf`·`tEXt`·`iTXt`·`zTXt`를 저장 전에 제거합니다. WebP는 형식만 확인하고 메타데이터는 제거하지 않습니다(클라이언트가 JPEG로 다시 인코딩해 보내므로 실사용 경로가 아님). | `src/server/services/media.ts` |
| **⑦ 번들러 없는 웹 표준** | `tsc`만으로 브라우저용 ES 모듈(`public/dist/`)과 서버 코드(`dist/`)를 따로 만듭니다. 같은 화면이 웹·PWA·Electron에서 그대로 동작합니다. | `tsconfig.client.json` · `tsconfig.server.json` |
| **⑧ 변경은 이력과 함께** | 신청 생성, 품목 변경, 운영 메모 수정, 고객 취소, 회원 연결은 같은 트랜잭션에서 `status_history`에 기록합니다. 문자 발송은 `sms_log`에 남기고 상세 화면 이력에 함께 보여 줍니다. 관리자 설정 변경은 이력을 남기지 않습니다. | `services/applications.ts` `addHistory` · `routes/admin.ts` |

### 서버 불변 규칙 (Invariants)
1. `admin_memo`·`admin_item_memo`·`lookup_pin_hash`는 어떤 고객 API(`/api/applications/lookup`, `/api/my/*`) 응답에도 들어가지 않는다.
2. 업로드 사진(`GET /api/uploads/:storedName`)은 관리자 세션(`fr_admin`), 소유 회원(`fr_customer`), 조회 쿠키(`fr_lookup`에 담긴 신청 ID) 중 하나가 없으면 존재 여부와 관계없이 `404`로 응답한다.
3. 품목 상태 변경은 **상태 전이표(1.5절)** 안에서만 허용하고, 그 밖의 전이는 `409 TRANSITION_DENIED`로 거부한다. 고객 취소는 모든 품목이 `PENDING`일 때만 가능하다.
4. 관리자의 품목·운영 메모 저장은 `version`을 함께 보내야 하며, 값이 다르면 `409 VERSION_CONFLICT`로 거부한다(최신 레코드는 응답에 담지 않고, 화면이 다시 불러온다).
5. `status_history`를 고치거나 지우는 API는 없다. 단, 신청이 지워지면(`ON DELETE CASCADE`, 예: 예시 데이터 삭제) 함께 지워진다.

## 1.3 시스템 논리 구성 및 모듈 책임

- **채널 계층**: ① 모바일·PC 브라우저 고객 화면(`/`), ② 설치형 PWA(`manifest.webmanifest`, `sw.js`), ③ 관리자 화면(`/admin`) 및 Electron 창(`desktop/main.cjs`).
- **Express 파이프라인 (`src/server/app.ts`)**: 보안 헤더(`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, 관리자 경로 `X-Robots-Tag: noindex, nofollow`) → `/api` 쓰기 요청의 `Origin`/`Referer` 호스트 검사 → `/api` 응답 `Cache-Control: no-store` → JSON 본문 `100kb` 제한 → (예시 데이터를 넣는 중이면 끝날 때까지 대기) → 공개·관리자 라우터 → JSON 404 → 공통 오류 처리기. 콘텐츠 보안 정책(CSP) 헤더는 두지 않았습니다.
- **모듈**:
  - `src/server/lib.ts`: `scrypt` 해시·검증(`hashSecret`/`verifySecret`, `timingSafeEqual`), HMAC 서명 쿠키(`Signer`, 상태 저장 없음), 쿠키 읽기·쓰기(`HttpOnly; SameSite=Lax`, HTTPS 요청이면 `Secure`), IP 기준 슬라이딩 윈도우 `rateLimiter`, 연속 실패 잠금 `FailureLock`, KST 날짜(`todayKst`, `dayDiff`).
  - `src/server/services/applications.ts`: 접수 검증·생성(접수번호 채번, 멱등성, 사진 저장 실패 시 파일 롤백), 고객 취소, 관리자 품목 처리(전이 가드 + `version` 잠금 + 이력), 운영 메모, 회원 연결, 고객·관리자 DTO 변환, 이력 조회(`sms_log` 합침).
  - `src/server/services/media.ts`: 매직 바이트 판정, JPEG `APP1` 제거, PNG 메타데이터 청크 제거, UUID 파일 저장, 롤백 삭제.
  - `src/server/services/sms.ts`: 솔라피(SOLAPI) 문자 발송. 환경 변수가 모두 있을 때만 켜짐.
  - `src/server/routes/public.ts` · `routes/admin.ts`: REST 라우트(3.4절). 대시보드 KPI·목록 필터·캘린더·통계·CSV는 라우트 안에서 계산합니다.
  - `src/server/demo.ts`: 예시 데이터 넣기(`seedDemoData`)·지우기(`clearDemoData`).
  - `src/server/db.ts`: 스키마 DDL·마이그레이션·관리자 계정·테스트 회원 생성, 멱등성 키 정리, 트랜잭션 헬퍼 `tx`(`BEGIN IMMEDIATE`).
- **저장소·외부 연계**: `node:sqlite` 파일 `data/gagudabang.sqlite`, 사진 `data/uploads/`, 서명 키 `data/.session-secret`(환경 변수가 없을 때 자동 생성). Vercel에서는 `os.tmpdir()/gagudabang` 아래에 두므로 인스턴스가 바뀌면 지워집니다. 외부 연계는 카카오 우편번호 스크립트(클라이언트), 솔라피 문자 API(서버), `tel:` 링크(관리자 상세)입니다.

## 1.5 공통 품목 상태머신 및 D-Day 산정 규칙

신청(`applications`)은 고객·주소·이사일을 담고, 업무 진행 상태는 **품목(`application_items.status`)** 단위로 움직입니다. 신청 전체의 대표 상태값은 따로 두지 않으며, 화면은 품목별 상태를 나란히 보여 줍니다.

| 상태 코드 | 화면 표기 | 진입 조건 | 다음 허용 상태 (`TRANSITIONS`) |
| --- | --- | --- | --- |
| `PENDING` | **접수대기** | 접수 직후 기본값 | `IN_PROGRESS`, `SCHEDULED`, `CANCELED` |
| `IN_PROGRESS` | **진행중** | 관리자가 판매·처분 진행 시작 | `SCHEDULED`, `COMPLETED`, `CANCELED` |
| `SCHEDULED` | **반출예정** | 반출 일정 확정 (**`pickup_schedule` 필수**) | `IN_PROGRESS`, `COMPLETED`, `CANCELED` |
| `COMPLETED` | **처리완료** | 반출·처리 종료 | 없음 (종결) |
| `CANCELED` | **취소·반려** | 고객 취소(전 품목 `PENDING`일 때) 또는 관리자 처리 (**새로 취소할 때 `public_notice` 사유 필수**) | 없음 (종결) |

- 같은 상태로 저장(처리 구분·날짜·메모만 수정)은 항상 허용합니다(`isAllowedTransition`: `from === to`).
- 관리자 화면의 상태 선택지는 현재 상태와 허용 상태만 보여 주고, 상태를 바꿀 때는 저장 전에 확인 단계(바뀌는 상태와 고객에게 보일 문구)를 한 번 더 보여 줍니다.
- 고객 진행률(%) 막대는 **구현하지 않음**. 고객 조회 화면은 상태 이름·판매 마감일·반출 일정·안내문을 글자로 보여 줍니다.

### D-Day 산정 규칙 (Asia/Seoul 날짜 기준, `todayKst`·`dayDiff`)
- **이사일 D-Day (`movingDday`)**: 미종결(`PENDING`·`IN_PROGRESS`·`SCHEDULED`) 품목이 있는 신청만 `이사일 - 오늘` 값을 갖고, 없으면 `null`. KPI `movingSoonApplications`는 이 값이 `3 이하`(지난 날 포함)인 신청 수.
- **판매 마감 D-Day (`deadlineDday`)**: `handling_type = 'RESALE'`이고 `status = 'IN_PROGRESS'`이며 `sale_deadline`이 있는 품목만 값을 가짐. KPI `deadlineAlertItems`는 `1 이하`(임박·경과)인 품목 수.
- **7일 내 반출 (`pickupIn7DaysItems`)**: `SCHEDULED`이고 `pickup_schedule` 앞 10자가 날짜 형식이며 `0 ≤ 반출일 - 오늘 ≤ 7`인 품목 수.
- **접수대기 (`pendingItems`)**: `PENDING` 품목 수.
- 화면의 D-Day 배지는 값이 `3 이하`이면 강조 스타일(`.dday.soon`)을 씁니다.

## 2.1 전체 화면 맵 (2개 화면 묶음 · 해시 라우팅)

화면 전환은 주소의 `#` 뒤 값(해시)으로 합니다. 서버는 `/`(및 `/index.html`)와 `/admin`만 HTML로 내보내고, 예전 주소 `/admin.html`은 `/admin`으로 넘깁니다(Express `301`, Vercel `308`).

## 2.5 고객 안내문 기본값 및 문자 문구 (단일 원천)

고객 조회 화면의 안내문은 품목의 `public_notice`이며, 비어 있으면 `src/shared/types.ts`의 `DEFAULT_PUBLIC_NOTICE`를 씁니다. 관리자 문자 문구는 `src/client/admin/main.ts`의 `smsText`가 만들고, 모든 문구는 `[가구다방] {고객명}님, 접수번호 {접수번호} '{품목명}' ` 뒤에 아래 본문을 붙입니다.

| 상태 / 문자 상황 | 고객 안내문 기본값 (`DEFAULT_PUBLIC_NOTICE`) | 문자 본문 (`smsText`) |
| --- | --- | --- |
| `PENDING` / 접수 확인 | 신청이 정상 접수되었습니다. 담당자가 가구 사진과 일정을 확인하고 있습니다. | 신청이 접수되었습니다. 담당자가 사진과 일정을 확인한 뒤 안내드리겠습니다. |
| `IN_PROGRESS` / 판매 진행 | 진행 중입니다. 확정 즉시 안내드립니다. | 판매를 진행합니다. 판매 마감일: {판매 마감일 또는 `[판매 마감일]`}. 진행 상황은 접수 조회에서 확인하실 수 있습니다. |
| `SCHEDULED` / 반출 일정 확정 | 방문 반출 일정이 확정되었습니다. | 반출 일정이 확정되었습니다. 일정: {반출 일정 또는 `[반출 일정]`} |
| `COMPLETED` / 처리 완료 | 반출 및 모든 처리가 완료되었습니다. 이용해 주셔서 감사합니다. | 반출과 처리가 모두 끝났습니다. 이용해 주셔서 감사합니다. |
| `CANCELED` / 취소 | 신청이 취소되었거나 진행이 어려운 품목입니다. 상세 안내를 확인해 주세요. | 신청이 취소되었습니다. 자세한 내용은 접수 조회에서 확인하실 수 있습니다. |

- 고객이 직접 취소하면 안내문은 `고객 요청으로 취소되었습니다.`(사유가 있으면 괄호로 덧붙임)로 저장됩니다.
- 관리자 화면의 안내문 칸에는 현재 상태의 기본 문구가 채워져 오며, 손대지 않고 상태만 바꾸면 빈 값으로 보내 새 상태의 기본 문구가 나가게 합니다.
- 위탁 판매·단순 처분을 나눈 별도 문구는 두지 않았습니다.

### 저장 형식 메모
- `created_at`·`updated_at`은 SQLite `datetime('now')`(UTC)입니다. 통계는 `datetime(created_at, '+9 hours')`로 KST로 바꿔 묶습니다.
- `moving_date`·`preferred_pickup_date`·`sale_deadline`은 `YYYY-MM-DD`, `pickup_schedule`은 자유 문자열(40자, 앞 10자가 날짜이면 캘린더·KPI에 반영)입니다.

- `phone`·`login_id`는 숫자만 남긴 번호입니다.
- 비밀번호·PIN 해시 형식은 `솔트hex:scrypt해시hex`(키 길이 32바이트)입니다.

## 3.3 핵심 서버 처리 규약

```typescript
// 1) 매직 바이트 판정 + 메타데이터 제거 (src/server/services/media.ts)
export function sanitizeUploadedImage(buf: Buffer): { mime: 'image/jpeg' | 'image/png' | 'image/webp'; clean: Buffer } {
  if (buf.length >= 4 && buf[0] === 0xff && buf[1] === 0xd8 && buf[2] === 0xff) return { mime: 'image/jpeg', clean: stripJpegApp1Segments(buf) };
  if (buf.length >= 8 && buf.subarray(0, 8).equals(PNG_MAGIC)) return { mime: 'image/png', clean: stripPngMetadata(buf) };
  if (buf.length >= 12 && buf.subarray(0, 4).toString('latin1') === 'RIFF' && buf.subarray(8, 12).toString('latin1') === 'WEBP') {
    // shortcut: WebP EXIF 청크는 제거하지 않음 — 클라이언트가 Canvas로 JPEG 재인코딩하므로 실사용 경로 아님, 직접 API 업로드 허용 시 보강
    return { mime: 'image/webp', clean: buf };
  }
  throw new AppError(415, 'UNSUPPORTED_MEDIA', '지원하지 않는 이미지 형식입니다. (JPG, PNG, WebP만 가능)');
}
// stripJpegApp1Segments: SOI 뒤 마커를 따라가며 SOS(0xDA)·EOI(0xD9) 전까지 APP1(0xE1)만 빼고 이어 붙임. 길이가 파일을 넘으면 415.

// 2) 품목 처리 트랜잭션 (src/server/services/applications.ts updateItemWorkflow 요약)
return tx(db, () => {                                   // BEGIN IMMEDIATE … COMMIT / ROLLBACK
  const cur = selectItem(itemId);
  if (!cur) throw new AppError(404, 'NOT_FOUND', '대상 가구 품목을 찾을 수 없습니다.');
  if (cur.version !== patch.version) throw new AppError(409, 'VERSION_CONFLICT', '다른 관리자가 먼저 변경했습니다. 최신 상태를 확인해 주세요.');
  if (!isAllowedTransition(cur.status, patch.status)) throw new AppError(409, 'TRANSITION_DENIED', `현재 상태(${cur.status})에서 ${patch.status}(으)로 변경할 수 없습니다.`);
  if (patch.status === 'SCHEDULED' && !pickup) throw new AppError(422, 'VALIDATION_ERROR', '반출예정 상태로 변경하려면 확정 반출 일정을 입력해야 합니다.');
  if (patch.status === 'CANCELED' && cur.status !== 'CANCELED' && !notice) throw new AppError(422, 'VALIDATION_ERROR', '취소·반려 사유를 고객 안내문에 입력해야 합니다.');
  if (patch.saleDeadline && patch.saleDeadline > app.moving_date) throw new AppError(422, 'VALIDATION_ERROR', '판매 마감일은 이사일 이전이어야 합니다.');
  updateItem(itemId, patch);                            // version = version + 1, updated_at = now
  addHistory({ type: 'ITEM_UPDATED', before: pick(cur), after: pick(patch), note });
  return { item, historyEntry };
});
```

### 접수 생성 순서 (`createApplication`)
1. `validatePayload`(필수값·형식·날짜·품목 1~20개) → 실패 시 `422` + `fieldErrors`.
2. 품목마다 `photos_{i}` 파일이 1개 이상인지 확인 → 없으면 `422`(`items.{i}.photos`).
3. `Idempotency-Key`가 저장돼 있으면 저장된 상태 코드·본문을 그대로 반환.
4. 사진을 하나씩 검증·저장하며 파일 이름을 기록(하나라도 거부되면 저장한 파일 모두 삭제).
5. 트랜잭션: KST 날짜의 기존 접수 수 + 1로 `FR-YYYYMMDD-NNN` 채번 → 신청·품목·사진·`CREATED` 이력·멱등성 키 저장.
6. 응답 `201 { requestCode, movingDate, preferredPickupDate, itemCount }`.

## 3.6 비기능 요구사항 · 인수 검수 기준 · 리스크 대응

- **응답 성능**: 조회 API `p95 ≤ 150ms`, 사진 5장 포함 접수 저장 `p95 ≤ 800ms`(`npm run perf`, `scripts/perf.ts`). 진행 기록상 500건·5,000건 시딩 기준 모두 통과.

### 필수 인수 시나리오 (검수 체크리스트)
1. **[비회원 다품목 접수]** 비회원이 가구 2품목과 사진을 올리고 PIN 4자리로 접수하면 접수번호(`FR-YYYYMMDD-NNN`, KST 날짜)가 발급되고 한 트랜잭션으로 저장된다.
2. **[중복 제출 방어]** 같은 `Idempotency-Key`로 두 번 보내도 신청은 1건이고 같은 접수번호가 돌아온다.
3. **[일정 가드]** 희망 반출일이 이사일보다 늦으면 서버가 `422`로 거부한다.
4. **[사진 보안]** GPS EXIF가 든 JPEG는 저장 시 `APP1`이 제거되고, 이름만 `.jpg`인 HTML·EXE 파일은 `415`로 거부되며 DB·디스크에 아무것도 남지 않는다.
5. **[PIN 조회와 분리]** 올바른 연락처+PIN이면 품목별 상태·마감일·반출 일정이 보이고, 응답 어디에도 내부 메모·PIN 해시가 없으며, 남의 사진 주소는 `404`다.
6. **[고객 취소 가드]** 전 품목이 `PENDING`이면 취소되고, 관리자가 한 품목이라도 진행으로 바꾸면 `409 TRANSITION_DENIED`다.
7. **[회원 자동 채움·건 연결]** 로그인 후 `#apply`에서 이름·연락처·기본 수거지가 채워지고, `#my`에서 비회원 건(접수번호+PIN)을 연결할 수 있다.
8. **[관리자 잠금·쿠키 분리]** 관리자 로그인 5회 실패 시 `429`, 같은 브라우저에서 고객이 로그아웃해도 관리자 세션은 유지된다.
9. **[품목 처리·동시성·캘린더]** 소파는 진행중(판매 마감일), 식탁은 반출예정(반출 일정)으로 저장하면 `#schedule`에 반영되고 이력이 남으며, 예전 `version`으로 저장하면 `409 VERSION_CONFLICT`다.
10. **[통계·일정·문자]** 직접 일정을 추가·삭제할 수 있고, 통계가 기간별로 집계되며, 문자 발송 설정이 있으면 발송 기록이 이력에 나온다.
11. **[멀티 플랫폼]** `390px`·`1440px` 화면, PWA 매니페스트, Electron 창(`npm run desktop`)에서 관리자 로그인까지 콘솔 오류 없이 동작한다.
