# 프로토타입 분리 기획안 (2단계: 관리자 웹 구성요소)

- 작성일: 2026-11-26
- 대상 산출물: `prototype/customer.html`, `prototype/admin.html`, `prototype/tokens.css`, `prototype/data.js`
- 전제(1단계에서 제안, 2단계 진행으로 확정 간주): 대상은 이사를 앞둔 개인 고객(주로 스마트폰)과 운영자(주로 데스크톱), 목적은 가구 접수와 진행 조회, 톤은 "차분하고 믿음직한" 하나.

## 1. 조사: 관리자 대시보드에 일반적으로 들어가는 것

| 구성요소 | 일반적인 형태 | 출처 |
| --- | --- | --- |
| 메뉴(내비게이션) | 데스크톱은 왼쪽 고정 사이드 메뉴, 메뉴 깊이는 얕게. 화면 폭에 따라 하단 탭(600 미만) → 레일(600~840) → 사이드(840 이상)로 바꾼다. | AdminLTE, Android 반응형 내비게이션 가이드 |
| 첫 화면 통계 | 맨 위에 지표 카드. 카드 하나에 지표 하나와 이전 기간 대비. 개수는 5~7개 이내(한 업체의 경험칙). 순서는 지표 → 추세 → 표. | AdminLTE |
| 목록(리소스 인덱스) | 제목과 화면 단위 버튼이 위, 필터·정렬·일괄 작업이 목록 바로 위, 행을 누르면 상세로 이동, 폭은 넓게. | Shopify Polaris |
| 표가 지원해야 할 과업 | 조건에 맞는 기록 찾기, 비교하기, 한 건 보기·수정·추가, 여러 건 일괄 처리. | NN/g |
| 빈 상태 | 지금 상태를 알리고, 사용법을 가르치고, 핵심 작업으로 바로 가는 길을 준다. 불러오는 중인데 "없음"으로 보이면 안 된다. | NN/g |
| 설정·계정·권한·감사 로그 | 운영자 계정과 역할별 접근 제어, 변경 기록, 세션 관리. | Adobe Commerce 관리자 문서 |
| 기본 골격 | 로그인, 목록, 상세가 최소 단위. 운영자가 쓰는 기능은 따로 기획해야 한다. | 위시켓 요즘IT, 크몽 제작 사례 |
| 색 | 색은 상태(정상·주의·위험) 표시에만 쓰고, 브랜드 색은 틀에만 쓴다. | AdminLTE |

## 2. 우리 서비스에 넣는 것

운영 규모는 운영자 1~2명, 하루 접수는 소량이고, 일의 핵심은 "이사일 전에 품목별로 판매·반출을 끝내는 것"이다.

| 넣는 것 | 내용 | 근거 |
| --- | --- | --- |
| 메뉴 5개 | 오늘, 접수, 일정, 안내 관리, 설정. 1440px은 사이드 메뉴, 768px은 아이콘 레일, 390px은 하단 탭. | 목적지가 5개 이하라 하단 탭에 들어간다(Android 가이드). 깊이 1단계(AdminLTE). |
| 오늘(첫 화면) | 지표 4개(접수대기 품목, 이사일 3일 이내, 판매 마감 임박·경과, 7일 내 반출 예정)와 "급한 순 접수" 목록. 지표를 누르면 그 조건의 목록으로 이동. | 지표는 위에(AdminLTE). 실제 앱의 KPI 4종과 같다. |
| 접수 목록 | 상태 필터, 검색, 이사일 임박순 정렬, 행을 누르면 상세. 접수 추가(전화 접수 대응)와 삭제. | Polaris 목록 구성. NN/g 과업 1·3번. |
| 접수 상세 | 신청자·수거지, 품목별 상태 변경(기존 상태 전이 규칙 유지), 판매 마감일, 확정 반출 일정, 고객 공개 안내문, 내부 메모, 변경 이력. | NN/g 과업 3번. 변경 이력이 감사 로그의 최소형. |
| 일정 | 달력에 이사일·판매 마감·반출을 세 가지 색 점으로 표시, 날짜를 누르면 그날 일정. | 서비스의 핵심이 날짜 역산이다. |
| 안내 관리 | 자주 묻는 질문과 공지사항을 각각 추가·수정·삭제. 자주 묻는 질문은 고객 홈에, 공지사항은 고객 화면의 공지 영역에 바로 반영. | 운영자가 쓰는 콘텐츠 기능은 따로 필요(위시켓). 공지사항은 사용자 결정으로 포함(2026-11-26). |
| 설정 | 사업자 정보(고객 푸터에 반영), 샘플 데이터 초기화. | 실제 앱의 설정과 같다. |
| 빈 상태 | 목록마다 "왜 비었는지"와 다음 행동 버튼. 검색 결과 없음과 구분. | NN/g. |
| 상태 색 | 접수대기·진행중·반출예정·처리완료·취소 다섯 가지에만 색을 쓴다. | AdminLTE. |

## 3. 넣지 않는 것

| 뺀 것 | 이유 |
| --- | --- |
| 추세 차트, 이전 기간 대비 | 지표가 "지금 처리할 건수"라 증감이 판단에 쓰이지 않는다. 데이터도 적다. |
| 일괄 작업 | 품목마다 상태와 날짜를 따로 판단해야 하고 건수가 적다. |
| 계정·권한 관리 | 운영자가 1~2명이고 실제 앱도 관리자 계정 하나다. |
| 알림 센터, 전체 검색 | 첫 화면의 급한 순 목록과 접수 목록 검색으로 충분하다. |
| CSV 내보내기 | 실제 앱에는 있지만 정적 프로토타입에서는 다루지 않는다. |

## 4. 데이터와 두 웹의 연결

- `data.js` 한 파일에 샘플 데이터를 두고, 화면에는 "샘플" 표시를 붙인다. 접수(신청자, 수거지, 이사일, 품목 목록), 자주 묻는 질문, 공지사항, 사업자 정보, 가구 종류.
- 처음 열 때 샘플을 `localStorage`에 넣고, 이후 추가·수정·삭제는 `localStorage`에서 한다. 설정의 "샘플 데이터 초기화"로 되돌린다.
- 관리자 → 고객 반영: 접수 상태·날짜·안내문은 고객의 진행 조회에, 자주 묻는 질문은 고객 홈에, 공지사항은 고객 화면의 공지 영역에, 사업자 정보는 고객 푸터에 나타난다.
- 고객 → 관리자 반영: 고객이 접수하면 관리자 접수 목록과 오늘 화면에 나타난다. 다른 탭에서 바뀐 내용은 `storage` 이벤트로 다시 그린다.

## 5. 컴포넌트 참고 (21st, 구조만 참고)

- Dashboard Shell: 접히는 사이드 메뉴가 좁은 화면에서 서랍으로 바뀌는 구성, 지표 카드, 정렬·필터 되는 주문 표.
- App Dashboard Layout: 사이드 메뉴와 지표 카드 배치.
- Empty State with Tabs, Invoice Empty State: 표 안에 들어가는 빈 상태와 다음 행동 버튼.

코드는 가져오지 않았다(코드 조회는 유료). 이름과 설명, 미리 보기만 봤다.

## 6. 3단계 기준안 (tokens.css)

- 파일: `prototype/tokens.css` (확인 전 초안).
- 글꼴 1종(Pretendard), 모서리 3단계(누르는 것 12px, 담는 것 16px, 알약형), 버튼 2종(주 버튼은 남색 면에 흰 글자, 보조 버튼은 흰 면에 테두리). 삭제 같은 위험한 동작은 보조 버튼 모양에 오류색 글자를 쓴다.
- 색은 남색·흰색 바탕 9개와 상태색 5쌍. 글자 대비는 모두 4.5 이상, 입력칸 테두리는 3 이상.
